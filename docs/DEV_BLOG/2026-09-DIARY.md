## 2026-09-19: A tester's LAN "create game" crash, and why it took a day to name

A tester reported that singleplayer worked perfectly while pressing "create
game" in the LAN lobby -- and in online -- closed the app instantly. They were
told to try the OpenGL backend instead of Vulkan; that was never going to help.

The engine log ended between two of `Shell::doPush()`'s own prints:

```
DEBUG: About to call TheWindowManager->winCreateLayout('Menus/LanGameOptionsMenu.wnd')
DEBUG: winCreateLayout returned: 0xb400007c56c020f0
<crash>
```

so the layout had loaded and the crash was inside `runInit()`. `crash.log` gave
`signal=11 fault_addr=0x8` and a backtrace of bare offsets.

Symbolized, it is:

```
crash PC      GameWindow::winGetEnabled() + 0x0
crash LR      PopulateStartingCashComboBox(GameWindow*, GameInfo*) + 0x1b0
backtrace[0]  InitLanGameGadgets() + 0x30c
backtrace[1]  LanGameOptionsMenuInit(WindowLayout*, void*) + 0xd4
backtrace[2]  Shell::doPush(AsciiString) + 0x168
```

`GameWindow` derives from `MemoryPoolObject`, which contributes a vptr and no
data, so on arm64 its first member `m_status` sits at +0x8 -- and
`winGetEnabled()` reads that and nothing else. `fault_addr=0x8` is a null
`GameWindow*`, exactly.

The null came from `ComboBoxStartingCash`, and the reason nothing complained is
that `winCreateLayout` does not fail on a control it cannot build:
`GameWindowManagerScript.cpp:2899-2905` stores whatever `parseWindow` returned,
`nullptr` included, and carries on to the next control. The lookups were all
guarded by `DEBUG_ASSERTCRASH`, which `Debug.h:206` compiles to `((void)0)` in
the shipped RelWithDebInfo build. So the layout loads, one control is missing,
and the first line that dereferences a gadget takes the process down.

Fixing that one pointer would have moved the crash three lines down; there are
more than twenty unguarded dereferences in that function alone, plus their twins
on the online screen. So instead: `InitLanGameGadgets` and `InitWOLGameGadgets`
now look everything up first, print the name of every control that is missing,
and answer `FALSE`; the screen declines to open and the player keeps a running
game and a readable log. Same bail-out `Shell::doPush()` already performs when
`winCreateLayout` itself returns nothing -- that guard just never covered a
layout that loads with holes in it. `PopulateStartingCashComboBox`, which all
three setup screens (LAN, online, skirmish) reach, guards itself too, since
"a null here kills the game" should not depend on every caller remembering.

Three of the online screen's asserts were also checking the wrong pointer --
`windowMap` was asserted four times in a row, standing in for
`checkBoxLimitSuperweapons`, `comboBoxStartingCash` and `checkBoxLimitArmies` --
so even a debug build would not have caught those.

### The part that actually cost the day

None of the above needed a device. Naming the functions did, and the crash log
could not do it: it printed `libmain.so+0x11f5268` and nothing else, although
the very same log contains

```
[texchurn] create #33 ... nearest_sym=_ZN21Render2DSentenceClass14Build_TexturesEv
```

-- the process can name its own addresses. `--strip-unneeded` removes `.symtab`
and the DWARF but leaves `.dynsym`, the engine builds with default visibility,
and the version script only hides `operator new`/`delete`, so `dladdr` resolves
ordinary engine functions in the shipped APK. The crash handler simply never
asked. It now does, after writing the offset-only line, so a `dladdr` that
deadlocks or faults costs the names and never the report -- the same
fault-tolerance trade the frame-pointer walk already makes.

Worse, the log's `[build compiled Aug 30 2026 16:38:03]` stamp was wrong.
ccache replays a cached object file with the preprocessor date baked into it,
which `GameEngine.cpp:858-867` already warns about; the only library whose code
layout agreed with the addresses in that log was built on 6 September.
Establishing that meant searching every APK committed under `apk/` for one whose
symbol table put a known offset inside a known function. The linker's build id
settles it in one field, so the crash log and the startup banner now carry it,
read out of our own mapped ELF image at load, alongside the CI run number that
names the artifact.

And the CI symbol bundle that would have answered this in a minute had expired:
`retention-days: 7`, copied from the APK step, where the 0.5 GB quota argument
genuinely applies. It does not apply to a few MB of gzipped text, and seven days
is shorter than the round trip on a tester report. Now 90.

### Not reproducible locally, and that is the point

The same sequence on the current build does not crash here. The LAN menu code
has not changed since March, so this is not something that was fixed in the
meantime -- the tester runs a Russian repack whose `WindowZH.big` presumably
lacks, or fails to parse, that one control. Which is precisely why the fix is
"the log names the missing control" rather than "add the control": we cannot see
their data, and the next tester will have different data again.

## 2026-09-20: The desync was never arithmetic

For weeks the cross-play desync was chased as a floating-point problem: arm64
does not compute what x86 computes, therefore lockstep cannot hold. A Windows
build was brought up and abandoned in service of that theory. It was the wrong
theory, and two measurements plus one overlooked directory ended it.

**Measurement.** The twelve transcendental expressions from `SimulationMathCrc`
were compiled for x86_64 and for aarch64 against the same glibc and run (aarch64
under qemu-user). All twelve agree bit for bit, in single and in double
precision, and so does the pathfinder's `10*sqrt(dx²+dy²)` followed by a cast to
int. Architecture is not the divergence. `-ffp-contract=off` is doing its job.

**The directory.** `/home/user/generalsonlinedevelopmentteam/gameclient` holds
the full source of the PC client we are trying to agree with. The problem was
never numerical analysis; it is a diff.

The diff found nine divergences. Three are live and move the logic RNG stream,
which is the quantity a lockstep desync amplifies fastest. All three are fixed
here, each verified line by line against the client rather than inferred:

`InstantDeathBehavior::onDie` ran its dead-state check first; the client runs it
last. When an object with AI is already dead, the client still draws for the fx
and ocl lists and then returns, while we returned having drawn nothing. Two
machines that disagree about how many numbers were taken from the logic RNG
cannot stay in sync. The same function also fired death weapons on scaffolds
under construction, which the client does not -- extra damage, extra objects,
another draw, on an action players take in the first seconds of a match.

`EMPUpdate.cpp` drew a particle's vertical offset from the logic RNG where the
client draws from the client RNG. `emitterCount` is at least fifteen, so every
EMP-disabled victim pulled fifteen-plus extra numbers out of the simulation
stream on our side and none on theirs. The comment a few lines below, which
correctly explains that the streams differ for `setInitialDelay`, reads as
though it covers this line too; that is probably why it survived.

`HelixContain::removeFromContain` lost its braces and a function call to a
`#if RETAIL_COMPATIBLE_CRC / #else / #endif` strip. What remained was a
brace-less `if` guarding only an assignment, and no `friend_setContainedBy`
call at all -- so a portable structure kept a dangling `m_containedBy` and
never cleared `m_containedByFrame`, which `Object::crc` hashes directly. A
mechanical port bug that put a divergence straight into the checksum.

The remaining six are recorded for follow-up: sniper-vs-structure damage and
the Aurora fuel bomb in `Weapon.cpp`, `MinefieldBehavior` destroying an object
the client keeps alive, and two of our own POSIX bugfixes (`OverlordContain`,
`ParkingPlaceBehavior`) that move CRC-hashed position state and so need a
version that does not.

Two conclusions worth keeping. The `USE_DETERMINISTIC_MATH` scaffolding in
`wwmath.h` should not be switched on: the PC client does not use GameMath or
fdlibm, so routing our side through them would replace a divergence measured at
approximately zero with an unmeasured one. And the existing
`(float)atan2((double)y, (double)x)` pattern is already bit-exact with what the
client's x87 produces at 24-bit precision -- "fixing" it to `atan2f` would
introduce disagreement on unit facing where there is none today.

Android played Android cleanly all along because both Androids share our
source. Android and the PC disagreed because our source and theirs describe
different simulations.

## 20/09/2026 — The desync measurement was off by one checkpoint

The user sent the map pack they had been testing on (`Casino - Resurrection`,
nine variants). Decompressing a `.map` is one screen of Python — `EAR\0` header,
RefPack stream, then the `CkMp` chunk tree whose layout is spelled out in
`DataChunk.cpp` and `Scripts.cpp` — so for the first time the scripts that run in
the first hundred frames could be read instead of guessed at.

What the map does explains why this one map was the one that failed. Group
`CounterRandom` holds two scripts, `Randomizer` and `Randomizer2`, neither of them
one-shot, each of which calls `SET_RANDOM_TIMER` on both the true and the false
branch. They run every logic frame, so the map draws from the logic RNG twice per
frame from frame 0 onwards — which is exactly the `ScriptEngine.cpp:6769 drew 200`
in the user's frame-100 tally, two draws times a hundred frames. A map that pumps
the shared random stream every frame amplifies any divergence immediately; a still
map hides one for a thousand frames. That was the whole of the "map-specificity"
worry, and it is a property of the map, not of a bug per map.

With that settled, the frame-0 object dump was worth a second look, and it said
something the earlier reading had skated over: twelve `SupplyPileSmall`, in six
pairs at identical positions, two of them at `0,0,0`. Six are the map's own
`Supply1..6`; six are `SupplyCasibo1..6`, which the `Supply Spawn` script creates
at `WaypointSpawnSupplyP0..P5` — and on a 2v2 map the last two waypoints do not
exist, hence the origin. Symmetric on both sides, so not the fault, but it did
prove the scripts had already run by the first checkpoint.

### The actual finding

The instrument was wrong. `RecorderClass::CRCInfo` on the PC client carries a flag
this port had dropped:

```cpp
m_skippedOne = !isMultiplayer;        // constructor
...
if (!m_skippedOne) { m_skippedOne = TRUE; return; }   // addCRC
```

In a network game the first `MSG_LOGIC_CRC` never makes it onto the wire, so a
multiplayer recording's checksum stream starts one interval later than the local
stream does during playback. The client compensates by discarding this device's
first local checksum. Without that discard every comparison is shifted by one
checkpoint, which produces precisely the two results this port has been reporting:
a mismatch at the very first comparison on a map whose state changes between
checkpoints, and ten consecutive perfect matches on a map where nothing moves.

A frame-matching scheme had been written here in September to avoid having to
guess whether the recording's first checksum survived. The guess was never needed.
The recording states its own game mode in its header, and the client reads it:

```cpp
Bool isMultiplayer = (m_originalGameMode == GAME_INTERNET || m_originalGameMode == GAME_LAN);
```

This port derived the same flag from `getSlot(localPlayerIndex)->getIP() != 0`,
because `CRCInfo` was constructed a few lines *before* the header fields carrying
the mode were read. So the one input that decides the pairing was a stand-in for a
value sitting unread in the file, and the pairing rule was then rebuilt around the
stand-in being unreliable.

Fixed by restoring the client's semantics exactly: construction moved below the
`maxFPS` read, `isMultiplayer` taken from `m_originalGameMode`, `m_skippedOne`
back, FIFO pairing back, and the arbitrary 16-entry queue cap removed (it could
silently drop recorded checksums and misalign the queue on its own). The frame
tags are kept, but only to label the log line. The trace now prints the recorded
game mode and the dropped first checksum, so the next log says which pairing rule
was in force rather than leaving it to be inferred.

What this costs: every desync conclusion drawn from a multiplayer replay before
today has to be re-taken. The `Trig.cpp` fix stands on its own measurement
(x87 at 24-bit mantissa versus bionic over 62801 angles, `sinf` differing on
1.236% of them and `(float)sin((double)x)` on none), but "frame 100 diverges" and
"1000 frames match" were both read through a shifted instrument.

### Also found, not on the critical path

Sweeping the simulation tree against the client with `diff --strip-trailing-cr`
(the file trees differ in line endings, which had been inflating the counts):

- `TurretAI::xfer` is version 1 here and version 2 in the client, which also
  serializes the base `StateMachine`. This affects save games, not the lockstep
  checksum — `XferCRC::xferSnapshot` calls `crc()`, not `xfer()` — so it is a
  real divergence in the wrong place to explain this one.
- `AIStates.cpp` compares `getNumFramesBlocked()` against
  `static_cast<float>(LOGICFRAMES_PER_SECOND)/4` where the client uses integer
  division. At 60 Hz both are 15; at 30 Hz ours is 7.5 and the client's is 7.
  Latent, and only on the 30 Hz engine.
- `Weapon.cpp` is missing the client's `SupW_AuroraFuelBombWeapon`
  `m_dieOnDetonate = TRUE` and its empty-Stinger-Site targeting rule.
- `AIUpdate.cpp` skips an unresolved locomotor name where the client throws.
  Checked against the user's log: no locomotor is missing on their install, so
  this did not fire.
- `StealthDetectorUpdate.cpp` and `ObjectCreationList.cpp` guard
  `createParticleSystem` against a null template where the client does not.
  Particle systems are client-side and absent from the logic checksum.

## 22/09/2026 — The locator's blind spot, and twelve supply piles

Spent the day making the checksum locator say something it could not say before,
and it mostly answered by ruling itself out.

**The backward walk rotates a difference, it does not shrink it.** I had read the
objects-section dump as evidence that the divergence lived inside that section,
because their walked-back value and ours agreed in the top eighteen bits at its end
— a 1-in-262144 coincidence, I thought. It is not: the walk rotates the difference
one bit per word, so a small word difference anywhere in the 79136 words after the
section lands as a small number at its boundary just as easily. Claim withdrawn, and
the dump is now the whole stream instead of one section, which removes the
assumption rather than arguing about it.

**The candidate lists are shorter than they look.** A single difference reappears
with the same implied delta every 32 positions, because that is where the rotation
comes full circle. Four of the twelve candidates at frame 100 were one hypothesis
wearing four hats (`5B030000`, `+859` after the byte swap, at words 5650, 5682, 5714
and 5746).

**The filter that does work: the same implied word at every checkpoint.** At the
true position the implied delta is frame-independent, because both machines agree up
to it. Intersecting eleven checkpoints leaves exactly three positions, and all three
are single elements of a rotation matrix — which cannot differ alone. Together with
the offline searches (transforms at up to three ULP, every three-word run, every
per-object constant offset: all zero hits) that closes the single-word story.

**What is left is an object list that is not the same list.** The failing replay's
map has 172 objects on frame 0 and 166 from frame 100 on, and the six that go are
exact positional duplicates of six survivors — the twelve `SupplyPileSmall` are six
pairs sharing coordinates to the last bit, four of them at (0,0,0). They appear
after the multiplayer starting units, so a script created them, on frame 0. If a
script that should run once runs twice here, every object created afterwards carries
an id the PC client never issued, and scattered single words differ all over the
stream — the one shape every search above is blind to.

So the new instrument is not more arithmetic, it is attribution: object creation and
destruction now name the script responsible, or `engine` when none is running.
`GXTrace` holds the running script's name for the duration of `executeScript`.

Also worth recording, since it cost an hour: the twelve skipped map reveals on that
map are `Player_5_Start` and `Player_6_Start` on a four-player map, and the twenty
others are players that do not exist in a 1v1. The PC client skips them too. Not a
lead.

### Later the same day: two leads closed, one of them mine to own

The attribution trace answered its question immediately, and the answer was no.
The twelve supply piles are the map's own doing: `Setup Scripts` creates six,
`Supply Spawn` six more at the same coordinates, `Supply Remove` destroys the
first six, all on frame 0, all in the map. The PC client runs the same three
scripts.

Then I read the same log's script-evaluation trace and announced that the shell
map's scripts were leaking into the game and spawning 44 phantom objects. They
are not. The shell map behind the main menu is a running game with its own frame
0, 1 and 2, and my trace printed only the frame number, so one log carried three
different games' opening frames under the same label and I segmented them as one.
Scoped to the replay's own lines, its frame 0 evaluates 869 scripts — the map's
852 plus 4, plus 86 from `SkirmishScripts.scb`/`MultiplayerScripts.scb` that the
engine loads by design — and none from the shell map. The traces now carry
`mode <GameMode>`; a frame number in this engine is not an identifier.

What did come out of the full-stream dump is worth more than either lead. A
deletion hypothesis — "we feed words they do not" — is not a search but an O(1)
test: if the two streams agree from word `j` onwards, their value at `j` must
equal ours at `p`. One hash join over all 85538 positions covers every position
and every length at once. Result: one candidate, at chance level (0.85 expected),
spanning 71067 words from the middle of a rock to the middle of the fog of war.
Meaningless. So the streams are not ours minus anything, and with the single-word
and multi-word searches already empty, one 32-bit number per hundred frames has
no more to give.

The next input is the `.rep` file. Nothing yet has checked that the game we build
for playback is the game that was recorded — and playback currently constructs
exactly one real player plus the observer, with one command centre and one dozer.
If the recording had more players, their starting units are words we do not have,
which is the one case the deletion test cannot see.

### The replay header, read at last

The `.rep` carries its `GameInfo` as plain text, so this cost one `head`:
`S=HMYSOREZ,0,0,TT,-1,2,-1,0,1:X:X:X:X:X:X:X:` — one human, seven closed slots,
no AI, and `SD=976636386` for the seed. So the recording had exactly one
participant, and the theory that the PC hashed some other player's buildings and
fog of war is gone.

The seed turned out to be checkable without a PC at all. `seedRandom` and the draw
ladder are twenty lines of integer arithmetic and `GetGameLogicRandomSeedCRC` is a
byte-wise CRC over the six-word state, so a short script can seed with the
replay's number and step. After exactly 109 draws the CRC is `DA7DB690` — which is
what our log prints at frame 0, and the independent RNG tally in the same log says
`draws=109`. The replay's seed reaches the logic RNG intact, the generator is
bit-exact against the PC's, and nothing draws before frame 0. The block that
resolves `startPos = -1` is identical to the client's and, in this game, takes the
branch that draws nothing.

I also checked the one thing I should have checked earliest: whether my own
instrumentation is in the checksum. `AI::crc` is the single `crc()` function that
differs from the client's, and the difference is trace lines and counters — no
`xfer` call added, removed or reordered. Clean.

What the full dump gave, beyond the deletion test, is a much cheaper unit of work.
A hypothesis confined to a window `[a, b)` costs `b - a` steps, not a pass over
85538 words, because their value at `b` is already known from the inverse walk and
needs no assumption about the rest. Twelve steps to test a transform. That made two
sweeps exhaustive: every object's twelve transform words at up to three ULP (4.8M
tests) and every plausible pair within 32 words (172M tests). Both zero.

Without the plausibility filter the pair sweep returned 23 hits where chance
predicts 0.05 — every one of them demanding that a structurally-zero word become
`0xFFFFFFFC`, or a byte inside a weapon's name change. That is the shape of the
remaining problem: a two-word hypothesis has one equation and two unknowns, so one
checkpoint admits a solution nearly everywhere. The fix is not a better filter but
more constraints, so the dump now fires on three checkpoints rather than one; a
static difference must hold at the same positions with the same deltas on all
three, and three 32-bit constraints are more than a pair of positions and deltas
can fake.

### Three checkpoints: 92% of the checksum cleared, by proof

The three-dump build paid off on the first log, and the first thing it showed was
about our side: between frames 100, 200 and 300 exactly one of our 85538 words
changes -- word 6402, the logic RNG state. The dozer has arrived; nothing moves.

That turns the PC's three checksums into a proof. Walk each one back through our
words to the end of the objects section: every walk crosses 79135 suffix words --
fog of war, player list, AI -- plus a different RNG word each time. If any of that
differed from the PC, three walks would land on three unrelated numbers. All three
land on `3091A52B`. So the fog of war, the player list and the AI are identical to
the PC's, the RNG state is identical on all three frames (our word is reached from
the replay's seed after exactly 310, 510 and 710 draws), and the whole difference
sits inside the 6402-word objects section, which is static from frame 100 on.

It also exposed a blind spot I had built myself. "The PC made a different number
of RNG draws" had never actually been tested, because both of my filters were
structurally unable to accept it: one demanded the same implied word on every
checkpoint, and an RNG word changes every frame; the other looked for fields
differing by a few units, and an RNG state CRC is an arbitrary number. Tested
directly now, and closed -- but the lesson stays: a filter that rejects every
candidate has to be checked for whether it could have accepted the right one.

Inside the objects section the three checkpoints add nothing, because the section
is identical on all of them -- one equation, however many times it is measured.
3.3 billion window tests of integer-shaped differences (single stamps, pairs moved
by the same delta, triples) produced only aliasing near the section's end and
nothing in its first 130 objects, the dozer included. I also checked the one line
in `Object::crc` that looked platform-shaped -- the upgrade mask fed in as
`sizeof(BitFlags<512>)` bytes of raw memory -- and it is 64 bytes on both MSVC and
libc++.

So the next step needs the user's PC, not mine: one solo recording on the same map
with no commands at all, and one with a single short dozer move. The first says
whether the initial state is right; the pair isolates what one move leaves behind.

### A second recording, and a candidate with a name

The user recorded a second game on the same map, the dozer driving and building
this time. The three-checkpoint proof held again -- difference inside the objects
section, everything after it identical to the PC -- and at frame 100 the two
recordings' objects sections differ in exactly two words, the dozer's X and Y. So
any static explanation has to reproduce both recordings: a second equation.

It finally put Gemini's terrain-height idea to a real test, and in doing so showed
my earlier sweep never had. The dozer sits at 1905, 1845, 30 -- exact integers --
and the filter that limited ULP perturbations to "arithmetically derived" elements
had skipped all three. Tested properly now across both recordings (position,
height, another pathfind cell, facing angle; 370M tests): nothing.

Then the natural family of multi-object differences -- one field of every object
of one template, shifted by the same amount. 406016 hypotheses, two survivors,
both on the map's two `AmericaCheckpoint` objects, both matching both recordings
to the bit. One says m22 is `0.99999994` on the PC where we have `1.0`: a one-ULP
difference in a computed rotation element of a quarter-turned object, which is
exactly what x87 and ARM disagree about. The other is its alias -- a zero word two
units low -- and it fits the same two recordings equally well.

Two recordings cannot separate them, and I measured why rather than assume it: a
static change produces the same end difference in both only when it sits in the
last few hundred words, and the checkpoints are right there. What separates them
is a checkpoint with a different object list, because that changes every running
value the difference passes through. The second recording has seventeen of those
after the building goes up. So the engine now tests each hypothesis itself at
every mismatching checkpoint and prints whether the result is the PC's number.
Same recording, one more run, and the candidate either holds seventeen times or
falls over.

Also corrected in the lesson: I had written that the start-position block draws
nothing from the RNG "which the tally confirms". It draws twice. I had printed
seven of the tally's eleven lines.

### Found it: the PC's Inv_Sqrt is an approximation

A stock map where the user just stood still matched the PC at every checkpoint.
It had no `AmericaCheckpoint` on it -- and the Casino arithmetic had just named
exactly those objects as the difference: both carrying m22 = `0.99999994` on the
PC. The dozer's start-of-game snap to a cell centre happened on the stock map too
and matched, so movement was out.

Then the game data said why only those two. `AmericaCheckpoint` has
`STICK_TO_TERRAIN_SLOPE`, so its matrix is built by `alignOnTerrain`, whose third
column is the terrain normal. The other quarter-turned objects on the map don't
have the flag. The normal comes from `Normalized_Cross_Product`, which calls
`WWMath::Inv_Sqrt` -- and `wwmath.h` gives that function an `_M_IX86` branch in
inline x87 assembly: a magic constant and three Newton steps. The PC client is
32-bit MSVC and takes it; we took `1.0f / sqrt()`. On flat ground the cross
product is `(0, 0, 1024)`; exact normalisation gives 1.0, the x86 routine gives
`0x3F7FFFFF`. Emulated under the client's `_PC_24`/`_RC_NEAR` that is precisely
the value the checksum inversion had demanded.

Checked on real x87 before touching the build: the portable replacement matches
x87 arithmetic at `_PC_24` over 6.9 million inputs with no differences, and a full
emulation of the checkpoint matrix before and after reproduces our dump and then
exactly the PC's. The same `#if` hid three more: `Float_To_Long` rounds on the PC
and truncated here, and `Sin`/`Cos` are `fsin`/`fcos` there and were `sinf`/`cosf`
here. All four now do what the reference does. `Inv_Sqrt` sits under every
`Vector3::Normalize()` the locomotor, physics and dozer AI use, which is also why
the second recording drifted further once the dozer started driving.

### The fix holds, and the second cause has the same shape

On the device: the idle Casino recording now matches the PC at all eleven
checkpoints, and the driving one matches at 100, 200 and 300 -- it diverged at 100
before. From 400 it still diverges, which is exactly when its dozer starts to
drive and turn.

Four full dumps of those later frames showed nothing in the objects section
moving except the dozer, and no ULP-sized drift of its transform reproducing the
PC's number -- expected, since a movement difference compounds. So instead of
searching the numbers I looked for the next class of "same source, different code".

The reference is built `/arch:SSE2`, so its ordinary float and double arithmetic is
IEEE SSE like ours; only explicit x87 assembly differs, and every other `__asm` in
Core turned out to be dead code. But 32-bit MSVC's CRT has no float
transcendentals at all -- `sinf(x)` is an inline `(float)sin((double)x)` -- while
bionic's `sinf` is a separate algorithm differing on about 1.2% of angles. And the
WWMath rotation helpers call `sinf`/`cosf` directly, twenty times over, and
`PhysicsUpdate` rotates a moving unit's matrix with them every frame. They now go
through `WWMath::Sin/Cos`. Unlike the first fix, this one cannot be checked
against a frozen value beforehand -- the effect compounds along the path -- so the
same recording decides.

### The rotation fix did nothing; the real one was hiding behind overloads

The Sin/Cos change in the WWMath headers produced exactly the same checksums at
400, 500 and 600 as the build before it -- bit for bit. So it touched nothing in
that window. Correct, harmless, not the cause. Comparing a new build's numbers
with the old build's is the cheapest measurement there is, and it said so at once.

Parsing `8.rep` itself gave the timeline: the dozer is selected at 262, the build
order for a power plant arrives at 342, and the first mismatch is 400. So whatever
diverges, it diverges while the dozer steers towards the site.

My first sweep for float transcendentals grepped for `sinf(`. But in C++ a plain
`atan2(dy, dx)` with `Real` arguments resolves to the float overload -- the NDK's
clang compiles it to `b atan2f` -- and nothing in the source says so. There are 59
such calls in the simulation directories, eight of them in `Locomotor`'s steering,
all going to bionic's single-precision routines while the PC client evaluates them
in double and rounds once. Instead of editing every site and missing the ones hidden
behind templates, the binary now carries its own `sinf`, `atan2f` and the rest with
the reference's semantics and hidden visibility, so every internal call binds to
them. The object file was checked before building; after building, `libmain.so`
must stop importing those names from libc.

A cancellation is a destruction. `onDozerCancelConstruct` refunds the cost and calls

A cancellation dies as `DEATH_NORMAL` from nobody, while combat brings its own damage
type, which picks the die modules. Once a cancel recording matches, a building
destroyed by weapons is the next thing to check.

### The leak in the float fix: sincosf

`ReferenceFloatMath` gives the binary the PC's semantics for `sinf`, `cosf` and the
rest. What I never did was check the finished binary: `libmain.so` still imported
`sincosf` from bionic. No source file calls it. clang merges `sin(a)` and `cos(a)` of
the same float argument into one `sincosf` call, and that call bypasses our
definitions. Four simulation files were affected, and all of them are 1.rep's
territory. `Geometry.cpp`'s box bounds decide which partition cells a building or a
construction site occupies. `BuildAssistant` decides whether and where a structure may
be placed. `AISkirmishPlayer` places the AI's base defences. `AIGroup` sends group
members to formation spots. Both `sincosf` and `sincos` are now defined in
`ReferenceFloatMath.cpp`, so any merge lands on the reference semantics. From now on
the import list is checked after every build.

### libm measured innocent

The math trace came back: 52,824 libm calls in frames 1900-1999, 123 call sites,
**zero** fragile, meaning none close enough to a float rounding boundary for any
accurate libm, the PC's included, to round it differently. Symbolised, the sites are
the ones expected: locomotors, debris physics, collision tests, the debris OCL, and
`findPositionAround` for the GLA worker leaving its building. The normalised code
diff against the client also came back clean for the whole simulation and the terrain
height path. What is left unmeasured is whether the PC reproduces its own recording.

### Same source, different compiler assumptions

With the maths and the code both measured equal, what remains is what each compiler
assumes about undefined behaviour. MSVC: no strict aliasing, signed ints wrap, null
checks after a dereference stay. clang -O2 assumes the opposite, and this engine
reads floats through `*(unsigned*)&f` right inside `REAL_TO_INT_FLOOR`. Compiling
every simulation file both ways changed the machine code of 276 out of 441. The build
now uses `-fno-strict-aliasing -fwrapv -fno-delete-null-pointer-checks`, the reference
compiler's semantics. `1.rep` will say whether any of it was live at frame 2000.

### Found it: NaN to int when debris lands

The user noticed it before the trace did: the mismatch comes when the debris lands,
not when the building breaks. The per-module fp trace then named the culprit:
`PhysicsBehavior` on `GenericDebris`, once per piece, as each came to rest.
`KillWhenRestingOnGround` kills the piece, and `SlowDeathBehavior::getProbabilityModifier`
divides overkill by max health. Debris has 0 max health, so that is 0/0 = NaN, which is
then converted to an `Int`. On the PC's x86 that yields 0x80000000, the probability
clamps to 1, and the following `GameLogicRandomValue(1, 1)` draws nothing. On ARM it
yields 0, the probability stays normal, and a random value is drawn. One extra draw per
piece of debris. The conversion now follows the reference's semantics
(`realToIntTruncRef`).

### CJK/Hangul/Arabic glyphs: per-glyph FreeType fallback

The font problem noted under the Chinese pack is fixed at the glyph level rather than by
swapping the game font. `FontCharsClass::Store_Freetype_Char` (`render2dsentence.cpp`) used to
render glyph 0 -- an empty box -- for any code point the base face lacked. It now asks
`Find_Freetype_Fallback_Face`, which lazily opens a short list of candidate faces at the base
font's pixel size and returns the first that has the glyph: `fonts/fallback.{ttf,otf,ttc}` from
the game-data folder (player-supplied), then on Android `/system/fonts/NotoSansCJK-Regular.ttc`
face 2 (SC; its glyph set also covers Hangul and kana), `NotoSansSC/KR`, `DroidSansFallback*`
and the Noto Arabic faces; on fontconfig platforms the matching families by name, accepted only
when fontconfig returns that family and not a generic substitute. Metrics (height, ascent) stay
the base face's, so line height does not change and the existing clip keeps taller CJK glyphs
inside their cell. Every face found is logged once as `[fontfallback] <path> face N family=...`,
and a font with no fallback at all logs that too, so a device log shows which case it is.
Latin/Cyrillic text is untouched: the fallback runs only when the base face returns glyph 0.

### Right-to-left text and Arabic shaping in Render2DSentenceClass

Needed before the Arabic and Persian packs can be shown at all: the sentence layout places one
glyph per code point, left to right, so Arabic came out unjoined and backwards. Rather than
rewrite the layout (wrapping, hotkey parsing, texture-edge splitting and the centred variant all
live in it), RTL text is handled around it:

- Before layout, `Prepare_RTL_Text` shapes Arabic letters into their presentation forms
  (U+FE70-FEFF, Persian letters from U+FB50-FDFF; isolated/final/initial/medial by joining type,
  harakat transparent, ZWJ/ZWNJ honoured and then dropped, lam-alef ligatures) and puts each
  word's characters in visual order. Latin/digit runs inside a word keep their order, brackets
  in RTL runs are mirrored, and a hotkey `&X` pair is never split. Checked on the host with a
  small harness: "سلام", "بالعالم", "(كلمة)", "اسم(&K)", "الـGLA", "می‌خواهم" all come out in
  the expected forms and order.
- After layout, `Mirror_RTL_Lines` reverses the word order of each line by mirroring chunk
  positions inside [0, widest line]: centred lines stay centred, wrapped paragraphs become
  right-aligned, and the extents the widgets measured stay valid. Chunks of one word split at
  the texture edge move together, runs of Latin words ("GLA", "(&K)", a number) move as one
  block, and the leading space the layout blits at the start of a word is cut off first. The
  separately drawn hotkey letter moves with its chunk.
- Line breaking still happens in logical order, which is what an RTL reader expects.
- If the fallback face has Arabic letters but not the presentation-forms block, the base letter
  is drawn unjoined instead of a box.

Text without Hebrew/Arabic code points takes none of these paths.

### Lists scroll with a finger

List boxes (map list, replays, the drop-downs of combo boxes, lobby lists) could only be
scrolled with the wheel or with the small arrows and thumb at their edge, which is fiddly on a
phone. A list already grabs the finger's down event and so receives `GWM_LEFT_DRAG` and
`GWM_LEFT_UP`; `GadgetListBox.cpp` now turns a vertical drag into scrolling on touch platforms.
Past a small threshold (1% of the screen height, at least 8px) the list follows the finger
pixel by pixel, clamped to the same bound the scroll bar's tracking uses, and the thumb is moved
with it; the release that ends a scroll selects nothing. A tap that never moved selects exactly

### Updates without a new APK: signed manifest on the `updates` branch

The launcher now updates settings and the engine from the repository. `UpdateManager.java`
fetches `manifest.json` and `manifest.json.sig` from the `updates` branch (raw.githubusercontent)
and verifies an ECDSA P-256 signature against the public key built into the app; the private
key is not in the repository (see docs/HOWTO/PUBLISH_UPDATE.md). A manifest may carry:

- `config`: written to `files/update/remote_config.ini`, read by the engine through
  `GXRemoteConfig.h`. The STUN and TURN lists in `NetworkMesh.cpp` now come from there when set.
- `engine`: build number (`git rev-list --count HEAD`, stamped into the APK as
  `assets/engine_build.txt` by the packaging script), gzipped `libmain.so`/`libmain60.so` with
  SHA-256 and size, and `requires_libs`, the SHA-256 of every other native library in the APK it
  was built from. `GeneralsZHActivity.loadLibraries()` loads the downloaded engine with
  `System.load()` in place of the APK's, and `getMainSharedObject()` points SDL at it; only when
  the build is newer than the bundled one and every required library matches this install.

Guards: a `serial` that never goes down (no replay of old manifests), SHA-256 on the engine
files, and a boot marker -- `files/update/boot_pending` is written before a downloaded engine
starts and removed by `MainMenuInit`; two starts in a row that never reach the menu mark the
engine bad and the APK's own runs again. Encryption was considered and rejected: the key would
have to ship in the APK, and nothing in the manifest is secret; what matters is that nobody
else can produce a file the launcher accepts.

Publishing: `scripts/update/publish-update.py` builds and signs the manifest (optionally from an
APK), `scripts/update/push-updates-branch.sh` replaces the branch with a single commit so engine
binaries do not accumulate, and the manual `Sign update` workflow signs with the
`UPDATE_SIGNING_KEY` secret when the key is not at hand. Checked end to end on the host: the
signature from `openssl` verifies against the embedded public key, and one appended byte makes it
fail. UI: Home → Updates (status, Check for updates, automatic check at launcher start).

**Offline.** Checked that the launcher needs no network: the update check, the GeneralsOnline
session refresh and the language download all run on background threads, and the engine and the
remote settings are read from local files only, so the last verified update keeps working
offline. A manual check without a network now says so in words ("No internet connection...")
instead of showing the raw exception, and is not recorded as a check.

### Cross-play broke with GeneralsOnline 092226_QFE1: the PC checksum now comes from update settings

"Play with PC players" claims the PC client's EXE checksum so PC lobbies accept this client. It
was compiled in as 3118172181, and the PC release of 26/09 changed it, so every PC lobby turned
the phone away again ("This Android build cannot join games hosted by the PC client").

The new number was computed, not guessed. `GlobalData::generateExeCRC()` on Windows runs the
engine's CRC (rotate left by one, add the byte) over the executable, then the version
(`major << 16 | minor`, 1.4 -- `BuildVersion.h` in the PC tree), then SkirmishScripts.scb and
MultiplayerScripts.scb. The same function without the executable and with version 1.0 -- which
is what this port reports for itself -- reproduces the device's own checksum 4265514697 exactly
(with 1.4 it is off by 128), which confirms both the algorithm and that the scripts are the same
on both sides. Over 092226_QFE1's GeneralsOnlineZH_60.exe it gives **524577083**.

So that the next PC release needs no APK, the number is now `pc_exe_crc` in the signed update
settings (`update/config.json`, read through `GXRemoteConfig.h`; the compiled fallback is the new
number), and `scripts/update/pc-exe-crc.py` computes it from a PC executable. Published as
manifest serial 2. A number written inside gx_pc_compat.txt still wins, as before.

### Community data patch: address in the update settings, version checked by the launcher

The GeneralsOnline community data patch was already downloaded from the GeneralsOnline CDN and
checked against the SHA-256 in its manifest, but the manifest address was compiled into the
launcher and nothing ever noticed a newer patch: a player kept the version they installed once.

Now the manifest address is `datapack_manifest_url` in the signed update settings (https only;
the compiled address stays as the fallback), so moving the CDN needs no APK. And the update check
also compares the installed patch with the CDN version, only on installs that already have the
patch: on Wi-Fi (an unmetered network) it installs the new patch by itself, on mobile data it
says a new patch is available, and **Check for updates** installs it. Published as manifest
serial 3.

### The PC checksum is computed on the phone from the PC release it has

Publishing `pc_exe_crc` by hand after every PC release still needs somebody to notice the release
and run a script. It does not need to: the community data package the launcher downloads *is* the
PC release, and `GeneralsOnlineZH_60.exe` is inside it. While extracting, the launcher now runs the
first half of `generateExeCRC()` over that executable (rotate left, add the byte; then version
1.4) and writes the state to `files/update/pc_exe_crc_seed.txt`; the engine adds
SkirmishScripts.scb and MultiplayerScripts.scb from its own file system and claims the result
(`[GX-CRC] PC exe checksum from the installed data package: ...`). Order of preference: a
number in gx_pc_compat.txt, then the computed one, then `pc_exe_crc` from the settings, then the
compiled number. The Java half gives the same state as `pc-exe-crc.py` on QFE2's executable
(1212249246, which with the scripts is 524577083). An install that already had the package
before this fetches it once more on the next check to compute the number.

### One decision for the data patch, shown in both places

The data patch had two independent update paths: the GeneralsOnline screen's "Network game data"
card (a manual Update button that never checked anything) and the new check in the Updates card.
Now `UpdateManager.checkDatapack` is the only place that decides: it records the newest CDN
version it saw, and an installed patch is out of date when that differs or when the PC checksum
has not been computed from it yet (`datapackUpdateWanted`). The Updates card shows the patch

the same "Check automatically" switch -- on Wi-Fi it installs with its progress in the card, on
mobile data it says "Installed X. A new version is out: Y" with an "Update available" chip. One
install lock (`DataPackInstaller.INSTALL_LOCK`) keeps the two from extracting over each other,
and the second one to get there finds nothing left to do instead of downloading it again.

Having one patch updatable from two cards was one place too many. Split by purpose instead: the

### Enter did not submit a text entry (join-game password)

Report: typing the password "213" into the join popup of a password-protected GeneralsOnline game
and pressing Enter on the Android keyboard did nothing. The field kept the text, so

### Native GLES translator: techniques borrowed from other D3D->GL translators

The user's own phone (Adreno, S3TC) already holds 55-60 fps at up to 2800 draws/frame on the
native GLES backend, so the target is weaker devices. Checked against what Valve's ToGL, WineD3D
and ANGLE do, and applied what fits `d3d8gles` (all in `gles_pipeline.cpp`; nothing borrowed from
their code, only the techniques):

- **Base-vertex draws.** D3D8's base vertex index now goes to `glDrawElementsBaseVertex` (ES 3.2
  core, or the OES/EXT extension) with the VAO's attribute pointers left at 0. Without it the
  offset is baked into the pointers, and the engine's shared dynamic vertex pool moves it on most
  draws: the 27/09 log showed 26-60% of all draws re-issuing every `glVertexAttribPointer`
  ("ptr-refresh").
- **A streaming ring for `DrawPrimitiveUP`/`DrawIndexedPrimitiveUP`** (4 MB vertices, 1 MB
  indices): unsynchronized appends, orphaned on wrap. Safe because a *UP draw's data is used by
  that draw only. It replaces two `glBufferData` respecifications per draw -- and the first of
  those two was redundant anyway.
- **Program binaries on disk** (`<HOME>/.cache/gx_gles_programs`), keyed on the generated shader
  source plus GL_VENDOR/RENDERER/VERSION; a binary the driver refuses is deleted and recompiled.
  Removes the compile hitch the first time an effect appears in a launch.
- **DXT1 at 16 bpp where S3TC is missing** (Mali): the software decode's RGBA8 is repacked to
  RGB565, or RGB5_A1 when the texture uses DXT1's punch-through alpha, decided on level 0 and kept
  for the whole mip chain. Half the memory and bandwidth; DXT3/5 stay RGBA8.
- `glGetError` once a second instead of every frame.
- Render-target readbacks (`glReadPixels`, a full GPU drain) are now counted and timed rather than
  replaced blind: the CPU shadow is the source of truth in this backend, and a GPU-side copy
  there needs evidence that it runs often enough to matter.

Every one of them can be turned off from the game folder: an empty `gx_gles_noopt.txt` disables
all, or it names the ones to disable (`basevertex upring progcache dxt565`). A new log line
`[d3d8gles] perf-opt:` reports what each did per window, and `[d3d8gles] optimizations:` at startup
says which are active on the device and why not.

Follow-up, 28/09: base-vertex draws are **off by default**. On the owner's Adreno (ES 3.2, the
core `glDrawElementsBaseVertex`) they took ~2400 draws/frame and pointer refreshes fell from
70-90 thousand per window to zero, with no fps change on a phone already at 60 -- and stencil
shadow volumes turned into long streaks and UI widgets flickered out. With only `basevertex`
named in gx_gles_noopt.txt, and with the file empty, both artifacts were gone, so it is this
one. Likely mechanism, not proven: the driver caches an index range per buffer and does not see
our unsynchronized dynamic-buffer writes. It stays available as an experiment
(`gx_gles_basevertex.txt`) for other GPUs. The ring for *UP draws and the program cache stay on:
the second launch loaded 22 programs from disk in 8.7 ms instead of compiling them.

its own vsync and is not covered by this.

The persistent build raised the frame rate and made the UI, buildings, units and effects flicker
(logs-23). Mobile GPUs are tile-based: a frame's draws run after the frame is submitted, so a draw
reads its buffer as it is at the end of the frame, not when it was issued. Through
glMapBufferRange the driver preserves what already-issued draws will read (copy-on-write); a
persistent mapping has no such protection, so every write to bytes an issued draw may read showed
up in that draw. The draw calls now record the highest byte of the current copy they may read
(`GLBufferState::gpuRefEnd`, from D3D8's minIndex/numVertices for the vertex buffer -- the whole
buffer when no count is given -- and the index range for the index buffer), and a write that lands
below it moves to a free copy first, refilled from the CPU shadow: the copy-on-write the driver
used to do. NOOVERWRITE appends past everything drawn stay a plain memcpy.

The flush-explicit attempt changed nothing either and is reverted (the copy-on-write stays). The
owner's observation pointed the way: the terrain, drawn from static buffers, never flickered;
everything drawn from dynamic buffers did. An independent read of the code (a separate agent,
given every attempt so far) found no data hazard in the persistent path -- the copy always matches
the CPU shadow when a draw is issued, VAOs are keyed by the GL name so a copy switch cannot bind a
stale one, and every draw path uploads first. What did change is that the driver no longer sees a
GL call when a dynamic buffer's contents change. glDrawElements carries no index range, so the
Mali driver scans the index buffer for min/max and caches the answer per buffer range until a
buffer-modifying call; the engine's dynamic index buffers refill the same offsets every frame, so
the cached range goes stale and vertices go unshaded -- dropped or garbled triangles, frame by
frame. It is the same mechanism already suspected for the Adreno base-vertex breakage. Dynamic
index buffers are back on the old path (a map/unmap tells the driver); vertex buffers stay
persistent. `gx_gles_persistentib.txt` opts the index buffers back in for testing another GPU.

while persistent vertex appends cost 0.4-1.4 ms. The owner also confirmed Adreno never flickered.
Instead of a per-GPU switch: dynamic index data now goes through an index stream. Each indexed
draw from a dynamic IB copies its own indices into the next unused bytes of one 4 MB persistently
mapped buffer and draws from there; the stream never writes a byte twice, so no (buffer, offset)
pair ever holds two different index lists and the driver's cached index range cannot go stale; a
full stream is replaced by a new buffer object (the old one deleted -- GL keeps its storage alive
for the draws in flight), so there is no fence and no wait. The IB's own GL storage is only used
when the stream is unavailable. Counted under `ring+index-stream` in `perf-upload`; `perf-opt`
reports stream renewals.

Stencil shadow volumes in one pass on GLES. D3D8 has no two-sided stencil, so
`W3DVolumetricShadowManager::renderShadows` draws every volume twice -- CULL_CW with INCR, then
CULL_CCW with DECRSAT. `d3d8gles_SetTwoSidedStencil(1, D3DSTENCILOP_DECR)` makes the translator
disable culling and apply D3DRS_STENCILPASS to front faces and the given op to back faces
(glStencilOpSeparate); the engine then skips its second loop. Both ops wrap, so the order in which
faces meet a pixel no longer matters; the result equals the two-pass one wherever a pixel sees at
least as many front as back faces, i.e. whenever the camera is outside the volumes. It returns 0
under DXVK or without glStencilOpSeparate, and the engine keeps its two passes.

Render thread for the native GLES backend (`include/gles_thread.h`, `src/gles_thread.cpp`). Every
GL call already went through `gles_dispatch.cpp`; there, on the engine's thread, a call now becomes
a command in a 16 MB single-producer/single-consumer ring (a lambda placed in the ring, pointer
arguments copied into it or onto the heap), and a render thread that owns the context runs them in
order. Calls whose result the caller needs (glGet*, glCreate*, glCheckFramebufferStatus, maps,
readbacks, program binaries) wait for the queue ahead of them; glGen* names come from pools refilled
64 at a time so object creation does not wait. The swap is queued too, and presenting frame N+1
waits only for frame N's swap, so the engine builds one frame while the driver consumes the
previous one. The unsynchronized buffer appends (`ensureVBUploaded`/`ensureIBUploaded`
non-persistent paths and the *UP ring) no longer map on the engine's thread: `gxrt::bufferWrite`
queues the data and the render thread maps, copies and unmaps. Fences used by the persistent
buffers are proxies: created in order on the render thread and polled there while it is idle, so
polling one from the engine's thread never waits. `glCheckFramebufferStatus` is asked only when a
render target's attachments change (tracked by a depth-renderbuffer generation), not on every
render-target switch. GL error checks run as queued commands. Android pause/resume: SDL backs the
context up and restores it on the thread pumping events, and sends WILL_ENTER_BACKGROUND and
DID_ENTER_FOREGROUND synchronously around that, so an event watch hands the context back to the
engine's thread before the backup and takes it again after the restore. `[d3d8gles] perf-thread`
reports the render thread's busy time and the engine thread's waits (previous frame, round trips,
ring space). Off with `gx_gles_noopt.txt` containing `thread`. Game logic is untouched: only when
GL calls run changes, not which ones or their order.

logs-30 (render thread): the menu battle on High went from median 38 to 48 fps (bottom decile 30
-> 34); the main scene fell from 18.5 to 13 ms and the swap from 1.5 to ~0 ms on the engine's
thread. Two problems. Rare flicker and triangles stretched across the screen for about a second:
the persistent vertex copies and the index stream are written by the engine's thread into
write-combined memory, and ARM holds such stores in the writing core's write buffer until a
barrier; the driver's submission used to follow the memcpy on the same core and drained it, now
the draw is issued from another core and the GPU could read stale bytes. The store-release that
publishes a command orders the stores for other CPUs only, so `gxrt::publishMappedWrites()` issues
a `dsb st` after each such memcpy (only while the render thread runs). Second, the render thread
was busy 19 ms median / 28 ms p90 for GL calls that cost ~9 ms on the engine's thread, and the
engine's thread waited 3-8 ms a frame for persistent-buffer fences: fences were polled only while
the render thread was idle, which in a heavy scene it never is, so copies never came free. It
now polls every 0.5 ms while busy too, and runs at nice -10, the priority Android gives its own
RenderThread. GitVerse mirror: the APK goes up inside a stored .zip, since phones saved a broken
file from GitVerse's raw endpoint while the same bytes installed from GitHub.

logs-31 (store barrier, busy fence polling, nice -10): median 49.7 fps, bottom decile 39 (34
before); persistent-copy waits went from 10-25 per window to 0-1 and sync waits from 3-8 ms to
~0.3 ms a frame. The render thread is still busy ~17.5 ms for ~8600 commands. The owner saw one
brief full-screen stretched triangle and a water flicker right after loading, far rarer than
before. One remaining way for it: the persistent path's hazard check trusts D3D8's
minIndex/numVertices as the vertex range a draw reads, which D3D never enforces; an understated
range leaves gpuRefEnd short and a later NOOVERWRITE write into the tail overwrites vertices a
queued draw still needs, and with the render thread the draw runs later than before. For a
persistent VB the indexed draw now scans its indices (already in m_bits) for the real maximum and
widens the recorded range; perf-opt reports how many draws understated it.

logs-33/34 (bisecting the render-thread artifacts with the existing switches): thread on with
persistent buffers off still showed long single stretched triangles; thread off with persistent
buffers on showed none. So the render thread exposes something, persistent mapping is not
required. The cause: the translator never recorded D3DLOCK_NOOVERWRITE. Every partial update of a
non-dynamic buffer went out as an unsynchronized append (map with GL_MAP_UNSYNCHRONIZED_BIT),
which is only right for NOOVERWRITE. A plain lock (neither DISCARD nor NOOVERWRITE) makes D3D wait
for, or rename away from, draws still reading the buffer; written unsynchronized, the bytes a
previous frame's draw was still reading changed under it. On one thread the CPU frame was slower
than the GPU's, so the GPU had always finished; with the render thread the CPU gets ahead and the
hazard shows. The persistent path already handled it (a write below gpuRefEnd moves to a free
copy), which is why only buffers outside it misbehaved. Unlock now records a plain lock
(`pendingSync`) and such appends go through glBufferSubData, the synchronized upload; perf-opt
counts them per frame.

logs-35 (synchronized plain locks): no change -- the engine makes no plain locks in that scene (the
new counter never fired), so that was not it; the code stays, being the correct translation.
The command ring was then stress-tested on the host (scratch test, ~670k commands with random
payloads, sync calls and presents, checked for order and content on the consumer side, also under
ThreadSanitizer): no loss, no reordering, no data race. What remains different from the
single-threaded path is where the persistent-buffer writes happen: the engine's thread wrote the
vertex copies and the index stream directly, while the draws that read them were issued later from
the render thread. `gxrt::writeMapped` now queues those writes (the data copied into the command)
and the render thread does the memcpy itself, in stream order, right before the draws -- where it
happened when everything ran on one thread. The store barrier is gone with it. The extra copy is
~5 MB a frame in the heavy scene.

logs-36 (persistent writes on the render thread): the owner saw no artifacts at all -- the cause
is confirmed: the engine's thread writing into persistent mappings while the render thread issued
the draws. Median 48 fps, bottom decile 43 (39 before), but uploads ~1 ms a frame dearer: the
data travelled in a heap Blob, and a full refill of a vertex copy is ~400 KB, an allocation big
enough to be mmap'd and page-faulted fresh every time. Two changes: `gxrt::writeMapped` now
carries the bytes inline in the command ring behind a small header (no allocation; split into
quarter-ring chunks), and a copy switch no longer rewrites the whole buffer from the CPU -- the
part outside the dirty range is copied from the previous copy with glCopyBufferSubData (added to
the dispatch), ordered after the draws still reading it, and only the dirty range is written by
the CPU; the two ranges never overlap. perf-opt counts GPU refills.

logs-37 (GPU refill + inline payload): the GPU refill was a failure on the Mali phone -- the UI
drawn from stale vertices (white bars, a giant logo, blocky menu), once a frame, which is the UI
buffer's DISCARD -- and fps fell to 40: a GPU write into a persistently mapped buffer is not kept
consistent by that driver, and the copy costs a render-pass break besides. Removed; copy switches
refill from the CPU again. The inline ring payload stays: full refills went from 1.8 to 0.2 ms a
frame on the engine's thread (the heap Blob's page faults were the cost, not the copying).

logs-38 (CPU refill + inline payload): no artifacts reported; the owner noticed the menu's loop
starting near 60 fps and running ~40 at the same spot a few minutes later. The log has no growth
anywhere (VAOs 80-100, textures ~250 after loading), the same ~1000-1200 draws a frame early and
late, but the engine's thread waiting on the render thread went from ~3 to 7-10 ms a frame: the
same work taking longer, the signature of thermal throttling. The render thread added heat for
nothing: each time it caught up it spun 200 yields (up to hundreds of microseconds, many times a
frame) before sleeping. The spin is now bounded at 30 us (and the engine thread's at 16 yields),
and `[GX-PERF-THERMAL]` logs each CPU's current clock and the hottest readable thermal zone every
perf window, so the next log can show throttling instead of us inferring it.

logs-39 (thermal line): throttling confirmed. The phone has two big cores; they ran at 2050 MHz at
the start of the menu loop (53-60 C, 47-55 fps) and at 1308-1796 MHz later (after 65-71 C, 35-42
fps) with the same 900-1200 draws a frame. Heat is proportional to work, so the remedy is fewer GL
calls per frame: ~9 per draw, and in about half of the model draws the vertex attributes were
re-pointed (4-5 calls) because the engine draws from its shared dynamic buffer at a new offset.
logs-40 with gx_gles_basevertex.txt: 7.3 GL calls per draw instead of 8.9, no attribute refreshes,
no artifacts; render-thread work times clock ~10% lower (the run was hotter: big cores at a 1530
MHz median against 1860, which hid the gain in fps). Base-vertex draws are now on by default on
Mali; gx_gles_noopt.txt containing "basevertex" still turns them off. Comparisons between builds
must start from a cool phone, or be normalised by the logged clock.
