## 2026-09-19: A tester's LAN "create game" crash, and why it took a day to name

A tester reported that singleplayer worked perfectly while pressing "create
game" in the LAN lobby -- and in online -- closed the app instantly. They were
told to try the OpenGL backend instead of Vulkan; that was never going to help.

The engine log ended between two of `Shell::doPush()`'s own prints:

```
DEBUG: About to call TheWindowManager->winCreateLayout('Menus/LanGameOptionsMenu.wnd')
DEBUG: winCreateLayout returned: 0xb400007c56c020f0
<crash>
```

so the layout had loaded and the crash was inside `runInit()`. `crash.log` gave
`signal=11 fault_addr=0x8` and a backtrace of bare offsets.

Symbolized, it is:

```
crash PC      GameWindow::winGetEnabled() + 0x0
crash LR      PopulateStartingCashComboBox(GameWindow*, GameInfo*) + 0x1b0
backtrace[0]  InitLanGameGadgets() + 0x30c
backtrace[1]  LanGameOptionsMenuInit(WindowLayout*, void*) + 0xd4
backtrace[2]  Shell::doPush(AsciiString) + 0x168
```

`GameWindow` derives from `MemoryPoolObject`, which contributes a vptr and no
data, so on arm64 its first member `m_status` sits at +0x8 -- and
`winGetEnabled()` reads that and nothing else. `fault_addr=0x8` is a null
`GameWindow*`, exactly.

The null came from `ComboBoxStartingCash`, and the reason nothing complained is
that `winCreateLayout` does not fail on a control it cannot build:
`GameWindowManagerScript.cpp:2899-2905` stores whatever `parseWindow` returned,
`nullptr` included, and carries on to the next control. The lookups were all
guarded by `DEBUG_ASSERTCRASH`, which `Debug.h:206` compiles to `((void)0)` in
the shipped RelWithDebInfo build. So the layout loads, one control is missing,
and the first line that dereferences a gadget takes the process down.

Fixing that one pointer would have moved the crash three lines down; there are
more than twenty unguarded dereferences in that function alone, plus their twins
on the online screen. So instead: `InitLanGameGadgets` and `InitWOLGameGadgets`
now look everything up first, print the name of every control that is missing,
and answer `FALSE`; the screen declines to open and the player keeps a running
game and a readable log. Same bail-out `Shell::doPush()` already performs when
`winCreateLayout` itself returns nothing -- that guard just never covered a
layout that loads with holes in it. `PopulateStartingCashComboBox`, which all
three setup screens (LAN, online, skirmish) reach, guards itself too, since
"a null here kills the game" should not depend on every caller remembering.

Three of the online screen's asserts were also checking the wrong pointer --
`windowMap` was asserted four times in a row, standing in for
`checkBoxLimitSuperweapons`, `comboBoxStartingCash` and `checkBoxLimitArmies` --
so even a debug build would not have caught those.

### The part that actually cost the day

None of the above needed a device. Naming the functions did, and the crash log
could not do it: it printed `libmain.so+0x11f5268` and nothing else, although
the very same log contains

```
[texchurn] create #33 ... nearest_sym=_ZN21Render2DSentenceClass14Build_TexturesEv
```

-- the process can name its own addresses. `--strip-unneeded` removes `.symtab`
and the DWARF but leaves `.dynsym`, the engine builds with default visibility,
and the version script only hides `operator new`/`delete`, so `dladdr` resolves
ordinary engine functions in the shipped APK. The crash handler simply never
asked. It now does, after writing the offset-only line, so a `dladdr` that
deadlocks or faults costs the names and never the report -- the same
fault-tolerance trade the frame-pointer walk already makes.

Worse, the log's `[build compiled Aug 30 2026 16:38:03]` stamp was wrong.
ccache replays a cached object file with the preprocessor date baked into it,
which `GameEngine.cpp:858-867` already warns about; the only library whose code
layout agreed with the addresses in that log was built on 6 September.
Establishing that meant searching every APK committed under `apk/` for one whose
symbol table put a known offset inside a known function. The linker's build id
settles it in one field, so the crash log and the startup banner now carry it,
read out of our own mapped ELF image at load, alongside the CI run number that
names the artifact.

And the CI symbol bundle that would have answered this in a minute had expired:
`retention-days: 7`, copied from the APK step, where the 0.5 GB quota argument
genuinely applies. It does not apply to a few MB of gzipped text, and seven days
is shorter than the round trip on a tester report. Now 90.

### Not reproducible locally, and that is the point

The same sequence on the current build does not crash here. The LAN menu code
has not changed since March, so this is not something that was fixed in the
meantime -- the tester runs a Russian repack whose `WindowZH.big` presumably
lacks, or fails to parse, that one control. Which is precisely why the fix is
"the log names the missing control" rather than "add the control": we cannot see
their data, and the next tester will have different data again.

## 2026-09-20: The desync was never arithmetic

For weeks the cross-play desync was chased as a floating-point problem: arm64
does not compute what x86 computes, therefore lockstep cannot hold. A Windows
build was brought up and abandoned in service of that theory. It was the wrong
theory, and two measurements plus one overlooked directory ended it.

**Measurement.** The twelve transcendental expressions from `SimulationMathCrc`
were compiled for x86_64 and for aarch64 against the same glibc and run (aarch64
under qemu-user). All twelve agree bit for bit, in single and in double
precision, and so does the pathfinder's `10*sqrt(dx²+dy²)` followed by a cast to
int. Architecture is not the divergence. `-ffp-contract=off` is doing its job.

**The directory.** `/home/user/generalsonlinedevelopmentteam/gameclient` holds
the full source of the PC client we are trying to agree with. The problem was
never numerical analysis; it is a diff.

The diff found nine divergences. Three are live and move the logic RNG stream,
which is the quantity a lockstep desync amplifies fastest. All three are fixed
here, each verified line by line against the client rather than inferred:

`InstantDeathBehavior::onDie` ran its dead-state check first; the client runs it
last. When an object with AI is already dead, the client still draws for the fx
and ocl lists and then returns, while we returned having drawn nothing. Two
machines that disagree about how many numbers were taken from the logic RNG
cannot stay in sync. The same function also fired death weapons on scaffolds
under construction, which the client does not -- extra damage, extra objects,
another draw, on an action players take in the first seconds of a match.

`EMPUpdate.cpp` drew a particle's vertical offset from the logic RNG where the
client draws from the client RNG. `emitterCount` is at least fifteen, so every
EMP-disabled victim pulled fifteen-plus extra numbers out of the simulation
stream on our side and none on theirs. The comment a few lines below, which
correctly explains that the streams differ for `setInitialDelay`, reads as
though it covers this line too; that is probably why it survived.

`HelixContain::removeFromContain` lost its braces and a function call to a
`#if RETAIL_COMPATIBLE_CRC / #else / #endif` strip. What remained was a
brace-less `if` guarding only an assignment, and no `friend_setContainedBy`
call at all -- so a portable structure kept a dangling `m_containedBy` and
never cleared `m_containedByFrame`, which `Object::crc` hashes directly. A
mechanical port bug that put a divergence straight into the checksum.

The remaining six are recorded for follow-up: sniper-vs-structure damage and
the Aurora fuel bomb in `Weapon.cpp`, `MinefieldBehavior` destroying an object
the client keeps alive, and two of our own POSIX bugfixes (`OverlordContain`,
`ParkingPlaceBehavior`) that move CRC-hashed position state and so need a
version that does not.

Two conclusions worth keeping. The `USE_DETERMINISTIC_MATH` scaffolding in
`wwmath.h` should not be switched on: the PC client does not use GameMath or
fdlibm, so routing our side through them would replace a divergence measured at
approximately zero with an unmeasured one. And the existing
`(float)atan2((double)y, (double)x)` pattern is already bit-exact with what the
client's x87 produces at 24-bit precision -- "fixing" it to `atan2f` would
introduce disagreement on unit facing where there is none today.

Android played Android cleanly all along because both Androids share our
source. Android and the PC disagreed because our source and theirs describe
different simulations.

## 20/09/2026 — The desync measurement was off by one checkpoint

The user sent the map pack they had been testing on (`Casino - Resurrection`,
nine variants). Decompressing a `.map` is one screen of Python — `EAR\0` header,
RefPack stream, then the `CkMp` chunk tree whose layout is spelled out in
`DataChunk.cpp` and `Scripts.cpp` — so for the first time the scripts that run in
the first hundred frames could be read instead of guessed at.

What the map does explains why this one map was the one that failed. Group
`CounterRandom` holds two scripts, `Randomizer` and `Randomizer2`, neither of them
one-shot, each of which calls `SET_RANDOM_TIMER` on both the true and the false
branch. They run every logic frame, so the map draws from the logic RNG twice per
frame from frame 0 onwards — which is exactly the `ScriptEngine.cpp:6769 drew 200`
in the user's frame-100 tally, two draws times a hundred frames. A map that pumps
the shared random stream every frame amplifies any divergence immediately; a still
map hides one for a thousand frames. That was the whole of the "map-specificity"
worry, and it is a property of the map, not of a bug per map.

With that settled, the frame-0 object dump was worth a second look, and it said
something the earlier reading had skated over: twelve `SupplyPileSmall`, in six
pairs at identical positions, two of them at `0,0,0`. Six are the map's own
`Supply1..6`; six are `SupplyCasibo1..6`, which the `Supply Spawn` script creates
at `WaypointSpawnSupplyP0..P5` — and on a 2v2 map the last two waypoints do not
exist, hence the origin. Symmetric on both sides, so not the fault, but it did
prove the scripts had already run by the first checkpoint.

### The actual finding

The instrument was wrong. `RecorderClass::CRCInfo` on the PC client carries a flag
this port had dropped:

```cpp
m_skippedOne = !isMultiplayer;        // constructor
...
if (!m_skippedOne) { m_skippedOne = TRUE; return; }   // addCRC
```

In a network game the first `MSG_LOGIC_CRC` never makes it onto the wire, so a
multiplayer recording's checksum stream starts one interval later than the local
stream does during playback. The client compensates by discarding this device's
first local checksum. Without that discard every comparison is shifted by one
checkpoint, which produces precisely the two results this port has been reporting:
a mismatch at the very first comparison on a map whose state changes between
checkpoints, and ten consecutive perfect matches on a map where nothing moves.

A frame-matching scheme had been written here in September to avoid having to
guess whether the recording's first checksum survived. The guess was never needed.
The recording states its own game mode in its header, and the client reads it:

```cpp
Bool isMultiplayer = (m_originalGameMode == GAME_INTERNET || m_originalGameMode == GAME_LAN);
```

This port derived the same flag from `getSlot(localPlayerIndex)->getIP() != 0`,
because `CRCInfo` was constructed a few lines *before* the header fields carrying
the mode were read. So the one input that decides the pairing was a stand-in for a
value sitting unread in the file, and the pairing rule was then rebuilt around the
stand-in being unreliable.

Fixed by restoring the client's semantics exactly: construction moved below the
`maxFPS` read, `isMultiplayer` taken from `m_originalGameMode`, `m_skippedOne`
back, FIFO pairing back, and the arbitrary 16-entry queue cap removed (it could
silently drop recorded checksums and misalign the queue on its own). The frame
tags are kept, but only to label the log line. The trace now prints the recorded
game mode and the dropped first checksum, so the next log says which pairing rule
was in force rather than leaving it to be inferred.

What this costs: every desync conclusion drawn from a multiplayer replay before
today has to be re-taken. The `Trig.cpp` fix stands on its own measurement
(x87 at 24-bit mantissa versus bionic over 62801 angles, `sinf` differing on
1.236% of them and `(float)sin((double)x)` on none), but "frame 100 diverges" and
"1000 frames match" were both read through a shifted instrument.

### Also found, not on the critical path

Sweeping the simulation tree against the client with `diff --strip-trailing-cr`
(the file trees differ in line endings, which had been inflating the counts):

- `TurretAI::xfer` is version 1 here and version 2 in the client, which also
  serializes the base `StateMachine`. This affects save games, not the lockstep
  checksum — `XferCRC::xferSnapshot` calls `crc()`, not `xfer()` — so it is a
  real divergence in the wrong place to explain this one.
- `AIStates.cpp` compares `getNumFramesBlocked()` against
  `static_cast<float>(LOGICFRAMES_PER_SECOND)/4` where the client uses integer
  division. At 60 Hz both are 15; at 30 Hz ours is 7.5 and the client's is 7.
  Latent, and only on the 30 Hz engine.
- `Weapon.cpp` is missing the client's `SupW_AuroraFuelBombWeapon`
  `m_dieOnDetonate = TRUE` and its empty-Stinger-Site targeting rule.
- `AIUpdate.cpp` skips an unresolved locomotor name where the client throws.
  Checked against the user's log: no locomotor is missing on their install, so
  this did not fire.
- `StealthDetectorUpdate.cpp` and `ObjectCreationList.cpp` guard
  `createParticleSystem` against a null template where the client does not.
  Particle systems are client-side and absent from the logic checksum.

## 22/09/2026 — The locator's blind spot, and twelve supply piles

Spent the day making the checksum locator say something it could not say before,
and it mostly answered by ruling itself out.

**The backward walk rotates a difference, it does not shrink it.** I had read the
objects-section dump as evidence that the divergence lived inside that section,
because their walked-back value and ours agreed in the top eighteen bits at its end
— a 1-in-262144 coincidence, I thought. It is not: the walk rotates the difference
one bit per word, so a small word difference anywhere in the 79136 words after the
section lands as a small number at its boundary just as easily. Claim withdrawn, and
the dump is now the whole stream instead of one section, which removes the
assumption rather than arguing about it.

**The candidate lists are shorter than they look.** A single difference reappears
with the same implied delta every 32 positions, because that is where the rotation
comes full circle. Four of the twelve candidates at frame 100 were one hypothesis
wearing four hats (`5B030000`, `+859` after the byte swap, at words 5650, 5682, 5714
and 5746).

**The filter that does work: the same implied word at every checkpoint.** At the
true position the implied delta is frame-independent, because both machines agree up
to it. Intersecting eleven checkpoints leaves exactly three positions, and all three
are single elements of a rotation matrix — which cannot differ alone. Together with
the offline searches (transforms at up to three ULP, every three-word run, every
per-object constant offset: all zero hits) that closes the single-word story.

**What is left is an object list that is not the same list.** The failing replay's
map has 172 objects on frame 0 and 166 from frame 100 on, and the six that go are
exact positional duplicates of six survivors — the twelve `SupplyPileSmall` are six
pairs sharing coordinates to the last bit, four of them at (0,0,0). They appear
after the multiplayer starting units, so a script created them, on frame 0. If a
script that should run once runs twice here, every object created afterwards carries
an id the PC client never issued, and scattered single words differ all over the
stream — the one shape every search above is blind to.

So the new instrument is not more arithmetic, it is attribution: object creation and
destruction now name the script responsible, or `engine` when none is running.
`GXTrace` holds the running script's name for the duration of `executeScript`.

Also worth recording, since it cost an hour: the twelve skipped map reveals on that
map are `Player_5_Start` and `Player_6_Start` on a four-player map, and the twenty
others are players that do not exist in a 1v1. The PC client skips them too. Not a
lead.

### Later the same day: two leads closed, one of them mine to own

The attribution trace answered its question immediately, and the answer was no.
The twelve supply piles are the map's own doing: `Setup Scripts` creates six,
`Supply Spawn` six more at the same coordinates, `Supply Remove` destroys the
first six, all on frame 0, all in the map. The PC client runs the same three
scripts.

Then I read the same log's script-evaluation trace and announced that the shell
map's scripts were leaking into the game and spawning 44 phantom objects. They
are not. The shell map behind the main menu is a running game with its own frame
0, 1 and 2, and my trace printed only the frame number, so one log carried three
different games' opening frames under the same label and I segmented them as one.
Scoped to the replay's own lines, its frame 0 evaluates 869 scripts — the map's
852 plus 4, plus 86 from `SkirmishScripts.scb`/`MultiplayerScripts.scb` that the
engine loads by design — and none from the shell map. The traces now carry
`mode <GameMode>`; a frame number in this engine is not an identifier.

What did come out of the full-stream dump is worth more than either lead. A
deletion hypothesis — "we feed words they do not" — is not a search but an O(1)
test: if the two streams agree from word `j` onwards, their value at `j` must
equal ours at `p`. One hash join over all 85538 positions covers every position
and every length at once. Result: one candidate, at chance level (0.85 expected),
spanning 71067 words from the middle of a rock to the middle of the fog of war.
Meaningless. So the streams are not ours minus anything, and with the single-word
and multi-word searches already empty, one 32-bit number per hundred frames has
no more to give.

The next input is the `.rep` file. Nothing yet has checked that the game we build
for playback is the game that was recorded — and playback currently constructs
exactly one real player plus the observer, with one command centre and one dozer.
If the recording had more players, their starting units are words we do not have,
which is the one case the deletion test cannot see.
